# Proposal: **Project Mapper** — Local Questionnaire-Driven Activity Mapping & Prioritization Tool

## 1. Purpose

Project Mapper is a lightweight, fully local tool that captures structured information about projects and activities through a guided questionnaire, and automatically produces four analytical outputs:

1. An **Impact/Effort Matrix** (per §3.1) for portfolio-level classification of initiatives.
2. An **Eisenhower Matrix** (per §3.2) for operational triage of activities, flagging critical elements that require more (or less) information before a decision can be made.
3. An **Organizational Mapping Diagram** that diagnoses which activities correspond to which sections/units of the organization (a swimlane/treemap view).
4. An **Overall Deliverables Timeline** (Gantt-style) consolidating all deliverable dates across projects.

The tool runs entirely on the user's PC. No external server, no cloud, no database engine to install, no internet connection required after setup.

## 2. Architecture Overview

### 2.1 Recommended option — Option A: Single Go binary + HTMX front-end (local-only)

```
┌────────────────────────── Your PC ──────────────────────────┐
│                                                             │
│  projectmapper.exe (single Go binary, ~10 MB)               │
│   ├─ Embedded web UI (Go html/template + HTMX, embed.FS)    │
│   ├─ Listens ONLY on 127.0.0.1:8787 (loopback, not a        │
│   │   network server — unreachable from outside the PC)     │
│   ├─ Data store: one JSON file (projects.json) or SQLite    │
│   │   file via pure-Go driver (modernc.org/sqlite, no CGO)  │
│   └─ Renders matrices, swimlanes, and timeline as inline    │
│       SVG generated server-side in Go templates             │
│                                                             │
│  Browser (Edge/Chrome/Firefox) → http://localhost:8787      │
│                                                             │
│  export/ folder                                             │
│   ├─ portfolio.xlsx   (via Python export script, optional)  │
│   ├─ diagrams .svg/.png                                     │
│   └─ backup .json                                           │
└─────────────────────────────────────────────────────────────┘
```

**Why this satisfies "no server":** HTMX needs an HTTP process to talk to, but that process is the same binary the user double-clicks, bound to `127.0.0.1` only. Nothing is installed as a service, nothing listens on the network, and closing the window stops everything. Functionally it behaves like a desktop app whose UI happens to be a browser tab.

**Stack (respects the Go / Python / HTMX-max constraint):**

* **Go** — application core: routing, data model, scoring engine, SVG diagram generation, XLSX export (via `excelize`, pure Go). Compiles to one `.exe` for Windows (or binary for macOS/Linux). Zero runtime dependencies.
* **HTMX** — all interactivity: questionnaire steps, drag-to-reclassify quadrants, inline editing, partial refresh of diagrams. No JavaScript framework; a single vendored `htmx.min.js` embedded in the binary.
* **Python (optional module)** — batch import/export utilities: ingest an existing Excel backlog, produce a formatted `.xlsx` report with `openpyxl`, or generate a PowerPoint-ready set of PNGs. Kept optional so the core tool works even without Python installed.

### 2.2 Fallback option — Option B: Pure Excel workbook

If a browser-based tool is undesirable, the same logic can ship as a macro-free `.xlsx` generated by a Python script:

* **Intake sheet** = the questionnaire (data-validated dropdowns).
* **Engine sheet** = formulas computing Impact, Effort, Urgency, Importance scores.
* **Matrix sheets** = scatter charts styled as the 2×2 grids (quadrant lines drawn as axes crossing at midpoints).
* **Timeline sheet** = stacked-bar Gantt.
* **Org map sheet** = pivot of activities × organizational section.

Limitations: no drag-and-drop, weaker diagrams, harder multi-user hygiene. Recommended only as an export target of Option A, not as the primary platform.

## 3. The Questionnaire (Intake Module)

The questionnaire is the single point of data capture. It is deliberately structured so that every question feeds at least one of the four outputs. Approximate completion time: 4–6 minutes per activity.

### Section A — Identification
| # | Question | Feeds |
|---|----------|-------|
| A1 | Project / activity name | All |
| A2 | Type: Project, Workstream, Recurring activity, Ad-hoc task | Matrix routing (see §4.3) |
| A3 | Owner (person) | Org map, Eisenhower (Delegate) |
| A4 | Organizational section/unit responsible (picklist, configurable) | Org map |
| A5 | Other sections involved (multi-select) | Org map (cross-unit links) |
| A6 | Short description / objective | Reports |

### Section B — Impact dimension (drives §3.1 Y-axis)
Each answered on a 1–5 anchored scale; the Impact score is a weighted average (weights configurable):
* B1. Contribution to strategic objectives (1 = none … 5 = directly enables a top objective)
* B2. Number of stakeholders / users affected
* B3. Financial or value effect (savings, revenue, risk avoided)
* B4. Consequence of *not* doing it

### Section C — Effort dimension (drives §3.1 X-axis)
* C1. Estimated person-days of work (banded: <5, 5–20, 20–60, 60–120, >120)
* C2. Number of sections/teams that must coordinate
* C3. Technical or procedural complexity (1–5)
* C4. External dependencies (none / some / blocking)

### Section D — Urgency & Importance (drives §3.2)
* D1. Hard deadline? (date, or "none")
* D2. What happens if delayed 30 days? (nothing / minor friction / escalation / breach or loss)
* D3. Is this important to *your* objectives or mainly to someone else's? (mine / shared / someone else's)
* D4. Could a competent colleague do this with a short briefing? (yes / partially / no)

### Section E — Deliverables & timeline
Repeating group (add as many as needed):
* E1. Deliverable name — E2. Due date — E3. Status (not started / in progress / at risk / done) — E4. Depends on (link to another deliverable)

### Section F — Information sufficiency (drives the "requires more/less information" flag)
* F1. Confidence in the estimates given above (1–5)
* F2. Which answers were guesses? (checkboxes over B1–D4)
* F3. What information is missing and who has it? (free text)

## 4. The Four Outputs

### 4.1 Impact/Effort Matrix (§3.1)

* **Computation:** Impact = weighted mean of B1–B4 (0–100). Effort = weighted mean of C1–C4 (0–100). Quadrant thresholds default to 50/50, adjustable with sliders (HTMX partial refresh redraws the SVG instantly).
* **Rendering:** SVG scatter; each activity is a dot sized by person-days and colored by organizational section. Quadrant labels: **Quick Wins**, **Major Projects**, **Fill-Ins**, **Thankless Tasks**.
* **Mitigating the known limitation** (two dimensions oversimplify): each dot carries hover/click detail showing risk (D2), dependencies (C4/E4), and strategic fit (B1) so the third dimensions remain one click away; an optional "strategic fit" color mode re-colors the same chart by B1.

### 4.2 Eisenhower Matrix (§3.2)

* **Urgency** derives from D1 (deadline proximity) and D2 (cost of delay). **Importance** derives from B1 and D3.
* Quadrants map to actions: **Do** (urgent + important), **Schedule** (important, not urgent), **Delegate** (urgent, not important — D4 suggests candidate delegates from A3/owner data), **Delete/Deprioritize**.
* **Information-need overlay (key feature):** activities with low F1 confidence or checked F2 guesses render with a dashed border and an "ℹ needs info" badge. A side panel lists them ranked by (Importance × Uncertainty), i.e., *the critical elements where gathering more information changes the decision most*. Low-importance, low-uncertainty items are conversely flagged "decide with what you have" — spending analysis effort there is waste.
* **Mitigating the binary-box limitation:** positions are continuous (scored 0–100), so items near the crosshairs are visually "on the fence" rather than forced into a box; a tolerance band around the thresholds lists borderline items for human review.

### 4.3 Organizational Mapping Diagram

* **View 1 — Swimlanes:** one horizontal lane per organizational section (from A4); activities appear as cards in their lane; cross-section involvement (A5) draws connector lines, immediately exposing coordination hotspots.
* **View 2 — Treemap:** sections sized by total person-days, revealing where organizational effort concentrates.
* Diagnosis rules (shown as automatic annotations): sections with >N cross-links → "coordination risk"; sections owning many *Thankless Tasks* → "review candidate"; activities with no section assigned → "orphaned".

### 4.4 Overall Deliverables Timeline

* Gantt-style SVG: one row per deliverable (E1–E4), grouped by project, colored by status, with today-line and dependency arrows.
* Filters (HTMX): by section, by quadrant (e.g., show only *Do* + *Quick Wins* deliverables), by date window.
* At-risk logic: a deliverable is auto-flagged if its status ≠ done and due date < today + 14 days, or if a dependency is at risk.

## 5. Data Model (single file, portable)

```json
{
  "sections": ["Operations", "Finance", "Legal", "IT", "..."],
  "weights": { "impact": {"B1":0.4,"B2":0.2,"B3":0.25,"B4":0.15},
               "effort": {"C1":0.4,"C2":0.2,"C3":0.25,"C4":0.15} },
  "activities": [
    { "id": "ACT-001", "name": "...", "type": "Project",
      "owner": "...", "section": "Finance", "involved": ["IT"],
      "answers": { "B1": 4, "...": 0 },
      "scores": { "impact": 72, "effort": 38, "urgency": 81, "importance": 66,
                  "confidence": 2 },
      "deliverables": [ {"name":"...","due":"2026-09-15","status":"in progress","depends_on":null} ] }
  ]
}
```

Everything lives in one JSON (or SQLite) file next to the executable — trivially backed up, emailed, or version-controlled.

## 6. Deliverables of This Proposal (what gets built)

| Phase | Deliverable | Effort |
|-------|-------------|--------|
| 1 | Go binary: data model, questionnaire UI (HTMX multi-step form), JSON persistence | ~1 week |
| 2 | Scoring engine + Impact/Effort and Eisenhower SVG matrices with adjustable thresholds and info-need overlay | ~1 week |
| 3 | Org swimlane/treemap diagram + deliverables timeline with filters | ~1 week |
| 4 | Excel export (Go `excelize`) and optional Python import script for existing backlogs; packaging (`.exe`, no installer) | 2–3 days |
| 5 | Pilot with a real backlog (15–30 activities), weight calibration, documentation | 2–3 days |

**Minimum viable scope** (if trimming is needed): Phases 1–2 alone already deliver the mandated core — *a mapping of activities and their prioritization* — with the org diagram and timeline as fast-follow.

## 7. Constraints & Guarantees

* **Local-only:** binds to loopback; works offline; no service installation; data never leaves the PC.
* **Stack ceiling respected:** Go (core), HTMX (UI), Python (optional import/export only). No Node, no frameworks, no database server.
* **Portability:** single executable + single data file; Windows/macOS/Linux builds from the same codebase.
* **Auditability:** all scoring weights visible and editable; every computed score traceable to questionnaire answers.

## 8. Risks

* Users may game 1–5 scales → mitigated with anchored descriptions per scale point and the confidence/guess flags (Section F).
* 2×2 frameworks oversimplify by design → mitigated via hover detail, continuous positioning, borderline bands, and alternate color modes (see §4.1–4.2).
* Localhost approach may confuse non-technical users → mitigated by a launcher that opens the browser automatically and a tray/console message "Project Mapper is running — close this window to stop."
